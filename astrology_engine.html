      These are two separate calculations from the current birth chart. Influence/Salience asks “how strongly does this planet/house shape the chart?” Benefit/Support asks “how constructively does it tend to operate in this chart?” A planet can therefore be highly influential but poorly supportive.

      Dynamic calculation & plug-in contract

      This version does not embed a lifetime dasha table. Every view is generated from the current birth profile and the registered system calculators.

      Runtime pipeline

      Birth profile → natal chart → Vedic/Saju anchors → lazy timing hierarchy → system score arrays → coverage-aware weighting → heatmap/action playbook.

      • Vedic hierarchy is recursive through Prana.
      • Western transits/profections are calculated at sampled dates.
      • Saju uses Four Pillars + Daeun + year + season.
      • Changing the birth profile regenerates everything.

      Calculation quality

      The browser first tries Swiss Ephemeris WASM and a BaZi library. If a provider cannot load, the engine remains functional using clearly labeled internal fallbacks. For boundary-sensitive professional work, use the provider badges and verify fallback results externally.

      System score contract

      Domains: Career, Wealth, Marriage, Family, Children, Vitality, Mind, Spiritual, Reinvention, Learning, Autonomy, Mentorship Return one value per supported domain: -2 strongly adverse/high friction -1 difficult/restructuring 0 mixed/neutral +1 supportive +2 strongly supportive null = unsupported / no coverage

      Register another dynamic system

      AstroHeatmap.addSystem({ id: "provider_jyotish", name: "OtherProvider: Jyotish", targetShare: 0.10, calculator: (ctx) => { // ctx.ms, ctx.profile, ctx.chart, ctx.domainNames return [/* 12 scores or nulls */]; } });

      Use provider-qualified names. The selected subset is automatically renormalized by domain.

      Load externally calculated static intervals

      Use this when another astrology engine/chat calculates the timing externally. Missing dates/domains remain uncovered by default, so the other selected systems automatically renormalize rather than being dragged toward zero.

      AstroHeatmap.addStaticSystem({ id: "otherprovider_jyotish", name: "OtherProvider: Jyotish", targetShare: 0.10, missingPolicy: "renormalize", intervals: [ { "start": "2026-09-01", "end": "2026-10-01", "Career": 1.2, "Learning": 1.5, "Autonomy": 0.8 } ] }); // Later replace/update its data: AstroHeatmap.setStaticIntervals( "otherprovider_jyotish", intervalArray );

      Contract: start is inclusive, end is exclusive. Scores are −2…+2. Unsupported domains should be omitted, not invented. Provider-qualified names are required to avoid collisions.

      Static JSON importer

      Vimshottari recursion

      childDuration = parentDuration × childLordYears / 120 Depth 1: MD Depth 2: AD Depth 3: PD Depth 4: Sookshma Depth 5: Prana

      Only the visible branch is generated, so a 100–120 year life horizon does not require hundreds of thousands of precomputed leaves.

      Saju conventions

      Daeun direction follows year-stem polarity + sex. Start age uses the traditional days-to-nearest-Jie ÷ 3 approximation unless you provide an explicit start age. The UI exposes Saju Yongsin and start-age overrides because schools differ.

      Handoff rule for future chats

      Do not remove either plug-in path. This engine must continue to support:

      • Dynamic plug-ins: a runtime calculator(ctx) function.
      • Static plug-ins: externally generated date intervals imported as JSON.
      • Coverage-aware reweighting when a static system is missing a date or domain.
      • Provider-qualified names such as Built-in: Vedic and OtherProvider: Jyotish.
      • Export of static intervals and their missing-data policy with the profile configuration.

      Regression invariants for future patches

      • For the Prashanth preset, Mercury/Venus Antardasha must validate to 05 Jul 2024 → 06 May 2027 (±1 day).
      • The year selector must remain grouped by Mahadasha; transition years may show both lords in the option label.
      • The dynamic ranking engine must reproduce the Prashanth regression target Mercury 87, Mars 82, Rahu 81, Saturn 79 without a profile-specific runtime override.
      • The dynamic ranking engine must reproduce the Prashanth regression target 11th 88, 8th 84, 12th 83 without a profile-specific runtime override.
      • Every ranking card must show both Areas and a short Description before the click-through detail.
      • City + country must auto-resolve latitude/longitude by default; manual coordinates remain an explicit override.
      • Dynamic calculator plug-ins and static interval plug-ins must both remain supported.

      Validation gate

      • Any future calculator patch must run the embedded six-chart golden suite before release.
      • Required anchors: Western Sun/Moon/Asc/MC; Vedic Moon/nakshatra/pada/starting Vimshottari lord; BaZi year/month/day/hour under the declared civil-clock convention.
      • Every MD→AD→PD→Sookshma→Prana parent must be partitioned exactly by its nine children with no gaps or overlaps.
      • ±1-minute synthetic perturbations must remain continuous.
      • If the suite fails, the UI must display UNVALIDATED/FAIL; do not hide failure behind fallback behavior.

      Cycle-family contract

      Scoring providers and timeline cycles are intentionally separate. A system may expose zero, one, or several cycleKeys. The UI deduplicates by cycle key across the currently selected systems.

      AstroHeatmap.addSystem({ id: "vedic_provider_2", name: "OtherProvider: Vedic", targetShare: 0.10, cycleKeys: ["vimshottari"], // same key = one shared Vedic timeline calculator: (ctx) => [...] });

      If two selected providers both declare vimshottari, the Cycle zoom menu shows one Vedic · Vimshottari option. Their score evidence remains independent in the ensemble.

      Add a genuinely new cycle family

      AstroHeatmap.registerCycleFamily({ key: "other_cycle", label: "Provider-neutral · Other cycle", contexts: [{id:"main",label:"Main cycle"}], groups: ({contextKey, profile, chart, calendarYear}) => [ {a:startMs,b:endMs,lord:"Cycle A",label:"Cycle A",path:["Other","Cycle A"]} ] });

      Then attach cycleKeys:["other_cycle"] to any providers that use that same cycle. Do not create duplicate timelines merely because the provider names differ.

      Natal-derived output invariant

      • Planet influence rankings, house rankings, natal placements, dashas, profections, Saju pillars and every other birth-chart-derived value must recalculate when the birth profile changes.
      • Prashanth's old ranking is a regression target only. It must never be injected as a special runtime ranking.
      • Provider-specific evidence may differ; shared astronomical/timing cycles should be identified by a provider-neutral cycle key.

      Time-zoom interaction invariant

      • The visible time selector is a cycle-aware tree: system/cycle family → context → grouping cycle → year.
      • Year grouping must be generated by the selected cycle family: Vimshottari by Mahadasha, Saju by Daeun, Western profections by 12-year profection blocks.
      • Provider duplicates sharing one cycleKey must never create duplicate timeline branches.
      • Custom dropdowns must close when the user clicks outside them or presses Escape.
      • Heatmap column headers must display date/date-range granularity appropriate to the current zoom.
      • Prana is terminal: render it in the dedicated readable navigator, not as a compressed horizontal lane or a fake “next level.”

      Ranking semantic invariant

      • Influence/salience and favorability/beneficence are separate dimensions.
      • Never label a high influence score as “best planet.” Rahu, Ketu, Saturn or Mars can rank highly because they strongly shape the chart while still being difficult or volatile.
      • Planet cards must visibly state the tone/context so users cannot infer that influence = goodness.

      Dual natal-ranking invariant

      • Always calculate and display two independent rankings: Influence/Salience and Benefit/Support.
      • Influence answers “how strongly does it shape the chart?” Benefit answers “how constructively does it tend to operate?” Never infer one from the other.
      • Planet benefit must be recalculated from the current chart using functional lordship, natural tendency, house placement, dignity, dispositor and close associations.
      • House support must be recalculated from the current chart using the house condition, its lord's support and occupant support.
      • Changing birth date, time, coordinates, ayanamsa or other natal settings must regenerate both ranking families. No profile-specific benefit ranking may be hard-coded.
      • Timing scores remain separate: a natal benefic can have difficult periods and a natal challenging planet can have productive periods.

      Natal dimension-map invariant

      • Rankings alone are not sufficient. The Rankings tab must also render Planet × life dimension and House × life dimension heatmaps.
      • Every cell must be dynamically derived from the current birth chart; never store a Prashanth-specific dimension matrix.
      • Cell color / S-score represents dimension-specific natal support (−2…+2). The I-score represents dimension-specific structural influence (0…100).
      • Planet domain influence combines overall natal influence with planet-domain semantics, occupied-house relevance and ruled-house relevance.
      • Planet domain support combines the independently calculated natal benefit score with the same chart-specific relevance paths.
      • House domain values combine house salience/support with that house's life-domain semantic profile.
      • The maps must respect the user's selected life-dimension filter and regenerate whenever the birth profile or dimension selection changes.

      House-system & Vedic-timing invariants

      • For Whole Sign, houses are assigned by zodiac sign difference from the Ascendant sign. Never use 30° sectors starting from the exact Ascendant degree.
      • For quadrant houses such as Placidus, use provider cusps when available; if unavailable, label the equal-house fallback explicitly.
      • Vedic dasha scoring must not use a generic planet-domain lookup alone. Each active MD/AD/PD/Sookshma/Prana lord must consume the current chart's dimension-specific support + influence metrics.
      • Domain productivity and overall beneficence are separate. A mixed functional planet may still be highly productive in a domain it strongly carries.
      • For the Prashanth Whole-Sign regression: Sun/Mercury = H4, Venus = H3, Mars/Saturn = H11, Moon/Jupiter = H12, Rahu = H8, Ketu = H2.

      Structural evidence → timing architecture

      Birth profile → structural layers → domain routing → integrated natal metrics → timing activation → system ensemble.

      • D1 is the primary natal layer. D9, D10, D2, D4, D12 and D60 are structural evidence layers, not separate timing systems.
      • Default routing: Career D1+D10+D9; Wealth D1+D2+D9; Marriage D1+D9; Family D1+D4+D12. Other dimensions stay mostly D1 with lighter relevant confirmation.
      • The same integrated Planet × Dimension metrics used in the natal map are consumed by Vimshottari MD/AD/PD/Sookshma/Prana scoring.
      • Changing Natal evidence to D1 only, D1+primary or Custom must recalculate both natal maps and the Vedic timeline.

      Generic structural-layer plug-in contract

      AstroHeatmap.registerStructuralLayer({ id: "provider_layer_x", name: "Provider: derived natal layer", systemFamily: "Western", // or Vedic, Saju, custom family role: "What this layer structurally represents", sensitivity: "moderate", domainWeights: {Career: 0.25, Learning: 0.15}, calculator: (ctx) => ({ influence: 0, // 0..100 support: 0, // -2..+2 relevance: 1, // 0..1 confidence: 1 // 0..1 }) });

      The engine separates structural evidence from timing families. A future Western, Saju or external provider can therefore register structural evidence without creating a duplicate timeline.

      Built-in Vedic divisional layers

      • D9 Navamsa: marriage/dharma and deeper planetary condition.
      • D10 Dasamsa: career, authority and professional expression.
      • D2 Hora: wealth/resources.
      • D4 Chaturthamsa: home/property/foundations.
      • D12 Dwadashamsa: parents/ancestry/family inheritance.
      • D60 Shashtiamsa: advanced corroboration only. It is half-degree sensitive, confidence-weighted, disabled by default, and its mapping convention is explicitly selectable because contemporary calculation conventions differ.

      Selection-scoped structural evidence

      • The visible Natal evidence dropdown is specifically a Vedic/Jyotish control and appears only while at least one selected system exposes structuralFamilies:["Vedic"].
      • The built-in Vedic/Jyotish system exposes that family; built-in Western and Saju do not.
      • If multiple selected Jyotish providers expose the Vedic family, the UI shows the D1/D9/D10/D2/D4/D12/D60 selector once.
      • Deselecting all Vedic/Jyotish providers hides the dropdown and prevents the Vedic natal maps from being presented as active evidence.
      • The generic structural-layer registry remains extensible to Western, Saju or custom systems, but those future families should surface through their own family-appropriate UI rather than this Jyotish-specific dropdown.
